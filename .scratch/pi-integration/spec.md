## Problem Statement

A user can start a VSR application and Pi independently, but cannot attach Pi to the running application through a supported framework interface to inspect its scene, observe an image, make controlled edits, and inspect the result. Existing scripting and scene-synchronization networking do not provide the required authorization, logical-session ownership, operation history, transactional editing, or recovery contracts.

This capability must work in headless and custom VSR applications. In vsrViewer, the human must also be able to see what the agent is doing, stop its control, and restore unwanted edits after Pi disconnects. Embedding Pi or building another chat client inside the viewer is not the goal.

The first useful workflow is: inspect a prepared scene and image, adjust existing materials and lighting to make the main object clearer, render a fresh result, and optionally restore the edits. Aesthetic improvement is a human judgment; execution, authorization, observation, resource bounds, and restoration must be objectively testable.

## Solution

Provide an explicitly enabled, headless VSR integration capability with an optional embedded MCP server on authenticated loopback access. Applications register exposed scenes, renderable views, operations, capability ceilings, and safe execution points. Pi is the first supported client, not a framework dependency. Use its installed MCP gateway where validation demonstrates compatibility; add a minimal trusted adapter only for a demonstrated gap.

The user starts the application, starts Pi, explicitly attaches using private connection information, and selects an exposed target. Pi remains the conversation interface. Structured operations perform bounded inspection, Agent Edit Batches, revision-pinned rendering, Batch Restoration, and explicit downstream resynchronization.

An Agent Edit Batch commits all scene changes or none. Conflicting stale edits reject; completed edits survive disconnects. Batch Restoration is conditional and one-way: it must not overwrite newer conflicting work or rewind unrelated state. Scene commit is distinct from downstream synchronization, so a post-commit synchronization error never falsely implies rollback.

A dedicated vsrViewer activity/results window consumes the same application-owned integration state available headlessly. It shows ownership, targets, operations, results, and recovery eligibility, with local controls to disable agent edits, disconnect, restore, and resynchronize. It does not own the integration or mirror the full Pi conversation.

## Implementation Decisions

### 1. Framework boundary and host integration

- The headless, transport-independent integration module owns registration, authority, logical sessions, operation admission/execution, activity, and restoration. The optional embedded MCP server adapts that API; it does not replace it or require a companion process.
- Applications explicitly register exposed scenes, renderable views, and operations and explicitly activate the endpoint. Linking alone does not activate control. A simple host may register one default target.
- Provide a standard application-Context convenience adapter, a viewer execution hook, and a blocking headless service-loop helper. Custom hosts can supply their own safe execution points.
- Context does not own the actual Image Pipeline or RenderIndex. Views must be registered independently; do not infer rendering support from Context alone. Each registered view names exactly one registered scene it renders in v1; synchronization health and recovery are scene-scoped, not inferred per renderer/index.
- Network threads parse/authenticate/admit requests but never access live scene state. The application services scene reads and writes at safe points coordinated with its own mutations and renderer. Do not silently relocate application state onto a worker thread or hold a transaction while the agent thinks or renders.
- ImGui, Lua, and Pi are not dependencies of the headless capability. Pi remains the first client. A minimal trusted Pi adapter is justified only by a demonstrated gateway gap.
- Public API/package names, MCP protocol version, HTTP/JSON dependencies, and concrete trusted-bootstrap integration are technical selections to validate, not claims about existing components.

### 2. Private launch descriptor and publication

Generate independent cryptographically random values each launch: a 256-bit launch credential and a 128-bit public launch identity. Never reload or reuse an old launch's values, even when reusing its endpoint port.

The descriptor is one UTF-8 JSON object of at most 4 KiB. Reject duplicate/unknown fields, unsupported versions, wrong types, or invalid encodings rather than coercing them.

| Field | Required v1 value |
|---|---|
| schema_version | JSON integer 1 |
| launch_id | 32 lowercase hexadecimal characters encoding the fresh public launch identity |
| scheme | String http |
| host | String 127.0.0.1 or ::1, not a DNS name |
| port | JSON integer in [1,65535], always explicit |
| path | String /mcp |
| launch_credential | Canonical unpadded base64url for 32 random bytes, 43 characters |

- Publish only in a validated owner-controlled private local runtime directory. The host may select a per-user OS runtime location or an explicitly configured directory; environment variables/path names alone do not establish trust. Before publication, open and validate the actual directory: it must be a directory owned by the application's effective OS account, with owner access sufficient for publication and no access for other untrusted accounts through permission bits or ACLs. Linux/POSIX directory mode 0700 and file mode 0600 are the baseline; account/ACL equivalents on other platforms require validation.
- Validate directory traversal/ancestry so another untrusted OS account cannot substitute, replace or redirect the selected directory or descriptor path. Reject symlink/reparse substitutions and unsafe parent components; use directory-relative, no-follow operations tied to the validated directory rather than a check-then-open pathname. Create any new private directory with restrictive access from creation; never repair unsafe pre-existing directories or fall back to an unchecked location. Exact directory names and platform APIs are implementation choices subject to these acceptance criteria and the platform-validation gate, not unspecified security policy. Same-account malicious-process isolation remains out of scope.
- Within that validated directory, use no-follow, exclusive fresh temporary-file creation with restrictive access from creation.
- Write complete bounded content, then atomically publish with no-replace semantics under the fresh name `vsr-mcp-<launch_id>.json`. Advertise its path only after listener, authentication, and authority checks are ready.
- Never follow, truncate, chmod, or overwrite a pre-existing destination. If `vsr-mcp-<launch_id>.json` already exists, fail activation closed; do not retry under another name. Reject unsafe parents rather than silently repairing them.
- Readers validate the opened regular file's owner, permissions, size, and strict schema; a path check before opening is insufficient.
- On orderly shutdown, remove only this instance's published file after checking its recorded platform identity without following links. Leave missing, mismatched, or uncertain entries untouched. Do not promise portable atomic compare-and-unlink against malicious same-account actors.
- Platforms without validated equivalent publication/read/cleanup guarantees report unsupported. A crash may leave a private inert descriptor; no cleanup daemon is required. Presence or age does not prove validity, while a copied descriptor for a still-running launch may still authenticate it.
- The descriptor contains no session secret/state, scene data, or timestamp used as validity proof. Viewer/startup output reveals the path, not credentials. No automatic application scanning is required.

### 3. Authentication, ownership, and transport

| Value | Purpose |
|---|---|
| Launch credential | Authenticates every integration/MCP request, including initialization and attachment |
| Public session ID | Fresh server-generated 128-bit identifier per attachment, encoded as 32 lowercase hexadecimal characters; echoed unchanged for correlation, never authority |
| Independent 256-bit session secret | Proves ownership of the current logical session |

- Every request carries `Authorization: Bearer <launch_credential>`. Session-scoped discovery/inspection, submission, renewal, cancellation, every operation-status/result lookup, and detach also require the current ID and secret through `VSR-Session-ID` and `VSR-Session-Proof: Bearer <session_secret>`. This includes minimal receipts and cross-session historical lookup: there is no sensitive/non-sensitive exemption from current session proof. Initialization/attachment use launch authentication before ownership is established; a coarse occupied attachment response is not an operation-status endpoint.
- Encode the session secret as canonical unpadded base64url. VSR identity/proof is distinct from native MCP transport-session identifiers and is not tied to one TCP connection.
- Trusted transport/client code consumes attachment/bootstrap and retains the secret privately across TCP reconnects. It must not be a model-visible tool returning the secret. A private response may carry bootstrap data; do not assume an unverified SDK exposes response headers. Validate the actual routing/integration before claiming support.
- The launch credential appears in the private launch descriptor defined above; the session secret does not. The descriptor contains no session fields. Neither secret appears in URLs, model-visible arguments/results, activity, or ordinary logs. The public session ID is correlation data, not a secret. Errors/logs must not echo credentials or whole request bodies. Scene strings and client summaries are data, not executable instructions.
- Derive the one allowed Host authority from the descriptor's exact host and port: `127.0.0.1:<port>` for its IPv4 endpoint, or `[::1]:<port>` for its IPv6 endpoint. Bind only that advertised address. The alternate address family is not an alias and must be rejected, as must DNS aliases, alternate spellings, default-port elision, forwarded-host substitution, and Origin-bearing requests. HTTP header names remain case-insensitive; absence of Origin does not bypass authentication.
- Enforce a single-family listener: descriptor 127.0.0.1 selects IPv4-only binding to that address; descriptor ::1 selects IPv6-only binding to that address, with IPv6-only socket behavior enforced before binding. Never bind wildcard addresses or automatically open a second-family listener. IPv4-mapped forms such as ::ffff:127.0.0.1 are forbidden in descriptors and Host authorities, not aliases. If the platform cannot enforce and validate these guarantees, reject activation before descriptor publication.
- VSR control transport is direct-only: no redirects, proxy routing, environment-proxy discovery, or endpoint substitution. Redirects are errors, not permission to forward secrets. This does not restrict unrelated application networking.
- This is authenticated local access, not isolation from malicious processes under the same OS account. Protection against other users and unsafe filesystem paths remains required.

### 4. Capabilities and logical-session lifetime

- Exactly one external logical-session slot exists, including inspection-only use. A second launch-authenticated attach returns coarse occupied status without incumbent ID, handles, scene data, results, or observer access.
- The host explicitly configures each target's read/render/edit/resynchronize grants as the capability ceiling for clients and viewer controls. Omitted capabilities are denied, including read. Without further host restrictions, those configured grants are effective immediately on attachment; attachment invents neither an automatic read-only profile nor an independently empty permission set. Current host restrictions narrow those grants, and unsupported/unexposed operations remain unavailable. Registration/exposure and current capabilities both apply; check ownership/capabilities at admission and safe-point execution, including after revocation.
- Restrictions belong to the application, not the session: Disable agent edits persists across detach, expiry and replacement attachment. Reconnecting cannot restore revoked permissions. Only the trusted host/local operator may explicitly relax restrictions within the configured ceiling; an external client cannot grant itself rights. Current policy applies throughout a session, not as a permanently cached attachment-time mask. Discovery exposes effective capabilities only for readable targets.

| Capability | Permitted target operations |
|---|---|
| read | Discover/inspect the registered target and read its activity/history and result payloads, including retained images |
| render | Request new renders of the registered view |
| edit | Submit Agent Edit Batches and Batch Restorations affecting the registered scene |
| resynchronize | Rebuild exposed downstream rendering state of the registered scene |

- Apply capabilities to the relevant registered scenes/views, not as an implicit all-target grant. Render, edit and resynchronize require read on their relevant target; enabling an action never silently grants read. Reject inconsistent launch configuration before activation. Discovery lists only targets the caller may read, and each discovery item returns the caller's current effective capabilities for that target; a capability change on a listed target is a returned-field change that invalidates discovery cursors. Withdrawing read makes dependent actions unauthorized and cancels newly unauthorized work under the existing safe-commit/cancellation rules.
- The authenticated owner retains renewal, cancellation of its own work, detach, and minimal operation-status receipts independently of scene permissions, never independently of launch/session authentication. The minimal receipt for the current session's own work is limited to its Operation Reference, operation kind, progress/terminal state, semantic outcome code, commit/no-commit information, and timing/cleanup/held-capacity metadata. Exclude scene values, names, object handles, version/revision tokens, Batch References, images, client summaries and free-form callback diagnostics. All other payload/history access requires current read permission for the relevant targets, including retained results reached through control/metadata lookup. Foreign-session records always require the all-target read checks below. Read revocation must not prevent releasing ownership or learning whether owned work committed.
- Local viewer actions use host authority within the launch ceiling and the same target safety checks, not the external session's temporary capability mask. External callers cannot select local authority.
- The lease defaults to 120 seconds without successful renewal; the client explicitly renews every 30 seconds independently of model thinking. Use the server's monotonic clock; successful renewal extends the lease from that time. Ordinary traffic does not renew. Attachment communicates the configured lease and renewal durations to trusted client code, which uses that cadence rather than assuming the defaults.
- Reject integration activation before endpoint publication if either duration is non-positive/non-finite or renewal is not earlier than expiry. Never silently clamp invalid configuration. Return a configuration error; the embedding host decides whether the application exits or continues with integration disabled.
- Renewal remains serviceable under full scene capacity or busy rendering through the separate bounded control path. The gateway, or an adapter if proven necessary, supplies this maintenance.
- Detach immediately releases logical ownership. Detach, whole-session revocation, or expiry permanently invalidates the session secret/cursors and cancels outstanding work, except an already-committing atomic edit finishes safely. A new attachment receives fresh identity/proof and a new request-ID namespace; old session authority/cursors never revive.
- Fresh inspection is a client workflow requirement, not an additional server authorization precondition. On a new attachment, supported clients must invalidate cached observations as current state and inspect the live targets before forming new version-pinned edit/render requests. Historical results alone do not satisfy that client refresh. The server does not require an inspection Operation Reference, session-bound observation proof, or evidence that the caller observed a value: it enforces current ownership/permissions, valid target identities and the operation's version/revision or restoration-eligibility checks. Handles and version/revision tokens are not invalidated solely by a session change; unchanged tokens may recur on reinspection and are accepted when all current checks pass. Authorized historical lookup and Batch Restoration may be invoked without a prior inspection operation; neither transfers old authority or turns historical data into fresh observations.
- Releasing ownership does not bypass serialized scene execution. Another controller's work still waits for a safe execution point after any prior committing operation.
- Disable agent edits narrows capabilities without ending the session: reject new remote edits/restorations and cancel queued ones, while permitted inspection/rendering continues. Other narrowing affects only newly unauthorized work.
- Local viewer/host access consumes no external logical-session slot. Multiple in-process callers/windows may submit integration actions, but their scene work shares the same host-serialized path as external work and rechecks permissions, versions and restoration eligibility at execution. If two local actors request one restore, only the first successful commit can consume its eligibility; the second cannot apply it again. Another process is an external client, even on loopback.
- Local Restore uses host authority after agent disable/detach but cannot exceed host target-mutation permission. The viewer's Disconnect control is local whole-session revocation: it releases ownership, invalidates secrets/cursors, and cancels outstanding work without Pi cooperation, subject to safe atomic completion and backend cleanup. Local revocation cannot be blocked by external capacity and is not an external-client privilege.
- Completed edits/history remain application-owned, not implicitly undone on disconnect. A result completed before cancellation remains completed. Outstanding non-atomic requests become canceled when cancellation is processed; late backend results cannot make them successful again. Attempt backend cancellation when supported, but retain resources until safe release and report busy where necessary.

### 5. Execution, admission, and resource accounting

The scene-work bound is one shared admission pool for all integration-submitted scene operations, whether submitted by an external client, a viewer window, or another in-process caller. It covers total admitted work, not only waiting requests. Each discovery page, inspection page, render, Agent Edit Batch, Batch Restoration, or resynchronization consumes one slot while queued, running, or yielded. One request retains one slot across inspection slices, independent of its item/edit count. Local Restore and Resynchronize use this same pool; neither local authority nor multiple windows creates separate capacity or an unbounded local queue.

Ordinary application work outside the integration API does not consume these integration slots, but must still coordinate safe scene/renderer access with integration execution. Local control actions, especially Disconnect/revoke, consume no scene slot and remain serviceable. This is not a scene-operation bypass: local Restore/Resynchronize may return busy before admission when all slots are occupied, including by backend cleanup. Disconnect does not force unsafe resource release or guarantee immediate restoration capacity.

A logically canceled/timed-out backend request retains its slot until resource release is safe, even indefinitely if necessary. Expose waiting-for-backend-cleanup state, elapsed waiting time, and held capacity. Report a backend fault only when the backend actually reports one; a long wait alone is not proof of failure. Control operations remain serviceable. Operator-managed backend/application recovery, potentially a restart, may be needed; no cleanup deadline, forced destruction or automatic recovery is promised. Do not hide held work in an unbounded extra pool. New requests reject busy before admission when capacity or necessary view resources are unavailable. Necessary view resources are the target view's backend rendering resources still held by logically canceled/timed-out work awaiting safe release. Applicable deadlines start at successful admission and include queue wait.

Attach, renewal, detach, authenticated cancel, and status/result lookup use separately bounded control/metadata work. It reads integration metadata or immutable retained results, not live scenes. Prioritize/coalesce renewal/cancel/detach so polling cannot starve lifecycle handling. Excess traffic returns bounded busy errors. Local operator revocation sets bounded in-process state independently; actual scene cleanup occurs at safe points.

All configurable limits are finite and positive. Default resource policy:

| Resource | Default |
|---|---|
| Lease / renewal cadence | 120 seconds / 30 seconds |
| Total admitted scene work | 32 requests shared by local/external integration callers, including queued/running/yielded work and retained backend work |
| External control/metadata work | 8 concurrent requests |
| Agent Edit Batch | 64 parameter edits |
| Request body | 1 MiB |
| Activity/restoration storage | 16 MiB combined, excluding retained image bytes; at most 1,024 activity entries and 32 restorable batches |
| Integration render dimensions | Positive integer width and height, each 1 through 1,024 pixels |
| Retained images | 32 MiB combined; retained image bytes count only here |
| Logical render deadline | 30 seconds from admission |
| Discovery/inspection page items | 64 default; maximum 256 |
| Serialized page including page metadata | 1 MiB |
| Serialized item / optional metadata within it | 64 KiB / 16 KiB |
| Optional display string | 4 KiB UTF-8, also subject to serialized-byte limits |
| Candidate visits per page request | 4,096 |
| Aggregate inspector scratch | 8 MiB global across all concurrently admitted discovery/inspection work; existing scenes and transport buffers are accounted separately |
| Inspection safe-point slice | At most 256 candidate visits; cooperative 2 ms yield target |
| Logical discovery/inspection deadline | 5 seconds from admission |
| Connection descriptor | 4 KiB |

- Enforce count, byte, and owned-memory limits independently while producing results. The 2 ms target is cooperative between bounded steps, not arbitrary C++ preemption. Logical timeouts do not authorize unsafe callback interruption.
- Evict oldest records safe to evict, including otherwise restorable records, visibly updating lost eligibility. Never evict storage required by active work. Byte accounting includes retained payloads, not just entry counts.
- Reject admission if slot/request/status reservations cannot fit. If an admitted edit later cannot reserve restoration storage, reject before commit without scene changes; its admitted ID remains consumed. Never commit an edit without required restoration storage.
- Eviction cannot re-enable old scene-operation request IDs. History and restoration state survive client disconnects but not application restart; expired restoration must be distinguishable from retained historical activity.

### 6. Identity and revision semantics

- Expose opaque object handles, object parameter-version tokens, and separate scene/view and registry/inspection revisions. Raw storage indices are not external identity.
- Handles cannot be reassigned to another object during a launch. Removal/replacement invalidates old handles. Defragmentation may remap correctly or explicitly invalidate, never silently redirect. Scene replacement/unregistration cannot leave obsolete handles addressing new objects. Earlier-launch authority cannot authorize later-launch edits.
- Edit conflicts are object-level: any parameter change on an affected material/light invalidates its inspected version, including another parameter or change-back-to-original. Changes on other objects alone do not invalidate the edit. Metadata-only labels are not parameter changes.
- Scene revisions cover render-relevant scene content, including other objects, layers, transforms, and animation. View revisions cover relevant camera, renderer, dimensions, and Image Pipeline configuration. Inspection returns scene/view tokens; a committed edit returns its resulting scene token. Change-back-to-original must not look unchanged.
- Registry/inspection revisions also cover returned metadata, returned parameter values, membership/order, parameter structure, registration, and handle mapping; any change to a returned field invalidates the cursor. They can change without edit-conflict or render revisions changing.
- Internal mapping algorithms and revision machinery remain implementation choices. Existing Object versions are building blocks, not proof of reliable external identity or tracking across the new failure paths. No persistent UUID/archive change is required.

### 7. Bounded discovery and inspection

- Use one incremental paging contract for target discovery and object/parameter inspection. An optional `page_size` integer requests 1 through the configured maximum (initially 256) items; omission selects the configured default (initially 64). Reject invalid requests rather than clamp. Byte/work budgets may return fewer items.
- Page size is a budget, not query membership/order. It may change on a continuation without alone invalidating the cursor; apply its default before canonical request comparison, and use a new request ID for changed request arguments. Providers must support stable enumeration with bounded individual steps; otherwise report unsupported. Do not materialize full-scene result lists or historical/per-client snapshots.
- Each continuation page is a fresh request with a new Operation Reference and its own admission slot. Cooperative processing slices within one page retain that page's ID/slot; no slot is held across client round trips merely for a continuation cursor. An identical retry with the same ID replays the retained page result, not another page.
- Cursors are opaque, authenticated against tampering, and bound to live session, query, target, and relevant registry/inspection revision. Their validity cannot outlive the session. No server-retained scene snapshot is required.
- Detect revision changes both between pages and during construction, including returned metadata changes. Return cursor stale and require restart; never silently skip vanished entries, merge revisions, or emit mixed-revision pages. Ordering/progress are deterministic only while the relevant revision is unchanged.
- Successful pages report revision, visited/returned counts, and either completion without a cursor or continuation with a stop reason: item, byte, or work limit. A filtering pass may return zero items with a progressing cursor. Hitting a limit is not completion. Invalid session/query/target/cursor is an explicit error.
- Enforce the resource table during construction. Mark optional truncation/omission, with original length only when cheaply available. Never truncate handles, types, revisions, conflict tokens, or other correctness-bearing values. Mandatory representation that cannot fit produces item-too-large, not silent omission. Do not scan/hash an entire oversized field to describe its truncation.
- Page requests consume normal scene slots and yield between bounded steps; renewal remains independent. At the 5-second admission deadline, end as timeout rather than false completion. No enumeration starts after expiry and late work cannot become success. Item/byte/work exhaustion returns continuation only with valid revision and saved progress.
- No bulk array export, unrestricted metadata retrieval, or filesystem browsing is implied.

### 8. Editable values and numeric conversion

The initial built-in edit surface is exactly the following existing-object parameters; hosts may expose a subset. Other built-in edits are deferred.

| Subtype | Parameter | Stored value and domain |
|---|---|---|
| Matte material | color | Three linear-RGB float32 components, each [0,1] |
| Matte material | opacity | Float32 scalar [0,1] |
| Directional light | color | Three linear-RGB float32 components, each [0,1] |
| Directional light | irradiance | Nonnegative float32 scalar, W/m² |
| Directional light | direction | Two float32 azimuth/elevation angles in degrees, each [0,360] |

Direction follows VSR's convention: azimuth zero points +Z and initially increases toward +X; elevation zero is the XZ plane and increasing elevation from zero initially rotates toward +Y. With radians used in trigonometry, direction is (sin(azimuth) cos(elevation), sin(elevation), cos(azimuth) cos(elevation)). The inclusive [0,360] domains are intentional; equivalent direction representations are allowed. Do not wrap or geometrically canonicalize angles before storage/version comparison. Changing stored angles is a parameter change even when the resulting physical direction is equivalent.

Numeric conversion has two representation-conversion stages: JSON number to binary64, then validated binary64 to binary32. The following four rules govern parsing, validation, rounding and zero/subnormal handling:

1. Correctly rounded finite IEEE-754 binary64 JSON-parser output is authoritative. Accept decimal/integer-looking numbers; reject booleans, strings, malformed/non-finite values, and coercion.
2. Before binary32 conversion, validate the binary64 value against the parameter domain and largest finite binary32 magnitude. Reject failures even if rounding would put them in range.
3. Convert deterministically using round-to-nearest, ties-to-even; do not rely on an unspecified ambient floating-point mode. Assert a finite in-domain result. Never clamp.
4. Accept finite subnormals and positive underflow to zero; normalize stored zero to +0. A negative nonzero binary64 input fails the nonnegative domain before underflow.

Examples: 0.1 accepts; opacity 1.0000000000000002 rejects; irradiance 1e39 rejects; 1e-46 stores zero; -0 stores +0. Exact decimal-lexeme range checking and equivalence to direct decimal-to-binary32 rounding are not promised; double rounding can occur.

The concrete double-rounding fixture uses irradiance input `1.00000005960464477539062582718061255302767487140869206996285356581211090087890625`, exactly 1 + 2^-24 + 2^-80. The required binary64-then-binary32 result is 1.0. Direct exact-decimal-to-binary32 rounding instead yields 1.00000011920928955078125; that is not this contract's oracle. Irradiance admits this input above 1, unlike color/opacity.

Unsupported parameters, incompatible types, invalid targets, and unauthorized operations reject before mutation. The host prepares the acceptance fixture procedurally: a sphere above a ground plane, matte materials, one directional light, and a fixed camera rendered with helide. The agent edits only the listed values; it does not import or construct this scene.

### 9. Operation identity, admission, and outcomes

- Every externally submitted scene operation uses the same request-ID scheme: discovery, inspection, rendering, edits, restoration and resynchronization. The client chooses `request_id` before submission as a JSON integer-valued number in [1,9007199254740991], not a string, boolean, fraction, or out-of-range value. A session has one server-owned high-water mark, initially zero, shared by all these operations. Clients normally start at 1; gaps are allowed.
- An **Operation Reference** is the pair of originating session ID and request ID. Its wire representation is an `operation_ref` object with `session_id` (the 32-lowercase-hex public session ID) and `request_id` (the numeric ID). Both are known before submission. Admission acknowledgements, status/results, cancellation and activity use the complete reference, not a connection-local/native MCP request ID or an unqualified number.
- A reference supplies correlation, not authority. A new submission's `session_id` must match the authenticated current session; external calls still require ownership proof and capabilities. TCP reconnection within the same logical session preserves references; a new session cannot reinterpret an old reference's number as its own work. Retained application history remains subject to host permissions, never a way to revive old authority. Local host actions retain distinct host-local correlation and do not consume an external session or its request counter.
- After authentication, ownership, envelope/schema, and capacity checks, admission atomically reserves a scene slot and bounded request/status storage, records canonical request identity, advances high-water, and queues. Pre-admission rejection consumes neither ID nor slot and does not advance high-water. A rejected ID remains usable only while above high-water: if request 5 gets busy and request 6 then admits, retrying 5 returns outcome_unavailable and never executes. Live scene/target/version validation remains at the host safe point; failures after admission consume the ID and remain queryable while retained.
- An admitted ID never queues or executes again. Compare parsed semantic fields, including operation, targets, expected versions, effective defaulted arguments and authoritative binary64 inputs—not only rounded storage values. Ignore JSON whitespace/member order and equivalent numeric spellings; normalize zero consistently. Identical retained requests replay their original status/results without consuming a scene-work slot, so replay stays available when the pool is full; conflicting content rejects with `request_id_conflict`, never executes, and leaves the retained record unchanged. Replaying a render or inspection result is not fresh work: retain its original revision/provenance, and require a new ID for a new capture or observation.
- At or below high-water, an unretained ID reports outcome unavailable and never executes. A higher ID may be unknown because its request is still in transit; unknown proves neither non-execution nor permission to renumber. Cancel of a not-yet-admitted reference cannot report confirmed cancellation. Whole-session revocation is the way to prevent delayed requests under that session from later admission.
- Clients serialize admissions for all external scene operations, not necessarily completion when an early acknowledgement is available. Otherwise wait for the terminal response. Send order alone is insufficient across connections; if 10 admits before 9, 9 cannot later admit. Control calls such as renewal, cancel, detach and status/result lookup do not consume this counter; cancellation/lookup name the target Operation Reference.
- A current session may use an older session's complete Operation Reference from the same application launch for read-only retained status/result lookup. Authenticate with current session proof, not the old secret. Require current read permission for every target covered by the record; the minimal-status exception for the caller's own work does not extend to another session's work. A record's covered targets are fixed per operation kind: inspection, edit, restore and resynchronize cover their one registered scene; render covers its registered view and that view's registered scene; a discovery page covers every target listed in it; a status/result lookup covers the targets of the looked-up record. Records covering more than one target (render, multi-entry discovery pages) are multi-target. Deny access to a multi-target record without permission for the whole record rather than silently returning a modified partial result. Preserve original operation kind and provenance; historical images are not fresh captures. Missing/evicted old records return outcome_unavailable, without added persistence or retention guarantees. Such lookup grants no cancellation, replay or execution authority over old work; new submissions still use the current namespace.
- After unavailable outcome/session loss, clients inspect and formulate new version-pinned work under valid authority rather than blindly replaying; this is the client refresh rule above, not an added server observation-proof check. Never wrap: after admitting the maximum ID, further scene work requires explicit detach/new attachment, with supported clients refreshing observations before new version-pinned edits/renders. Authorized historical lookup and restoration retain their separately defined checks. Control/metadata and retained-result queries remain available under their normal permissions; fresh scene inspection itself requires a new request ID.

Required outcomes must be machine-readable and stable rather than parsed from English. Freeze these semantic code names for the existing named outcomes: `occupied`, `busy`, `cursor_stale`, `superseded`, `outcome_unavailable`, `already_restored`, `item_too_large`, `conflict`, `request_id_conflict`, `cancelled` (this exact spelling, although prose uses "canceled"), `timeout`, `session_expired`, `unknown`, `sync_required`, `applied_with_sync_failure`, `unauthenticated` (missing/invalid launch credential), `invalid_session_proof` (missing, wrong or stale session proof), and `forbidden` (valid proof but a required capability is absent or unexposed). The headless API returns these three rejection codes directly; the adapter maps them to its carrier without collapsing them. Report operation progress/state separately where work is not terminal, using these frozen non-terminal state names: `queued`, `running`, `yielded`, `synchronizing`, and `awaiting_cleanup` (logically canceled/timed-out work retaining resources until safe release). Scene synchronization states are the frozen names `ready`, `needs_sync`, `synchronizing`, and `failed` (state names, distinct from the `sync_required` render outcome code). Retained status/results identify operation kind, including when read by a later session. Keep one conflict code for edit and restoration precondition failures; both mean no scene mutation occurred. Operation kind distinguishes these cases without English parsing; finer structured reasons may be added but no new mandatory conflict-subcode taxonomy is required. Restoration eligibility still distinguishes conflicting, consumed/restored and expired records. Mutation outcomes must explicitly distinguish scene commit from no commit, even when synchronization fails. Human messages are explanatory only. The validated adapter selects and documents the HTTP/MCP carrier, payload placement, and mappings (including further authentication/configuration/validation errors) without weakening these semantics; this is a binding deliverable, not an invented second transport protocol.

### 10. Agent Edit Batches and downstream synchronization

An **Agent Edit Batch** is one explicitly submitted group of edits that commits in full or leaves affected scene state unchanged. It is not a multi-turn task or VSR's existing notification-only update batching.

Each committed batch has an application-owned **Batch Reference**: a public object containing `launch_id` (the descriptor's public launch identity) and `batch_id` (a server-issued 32-lowercase-hex identifier unique within that launch, never reused after eviction). Publish it as `batch_ref` with the committed edit result and activity record, including applied-with-synchronization-failure. Keep the original edit's Operation Reference as provenance for external work, or host-local correlation for local work; neither replaces the Batch Reference. The reference identifies the retained restoration record independently of operation-result retention or client lifetime. It grants no authority, survives client disconnect only while its record is retained, and is invalid after application restart.

- At the safe execution point, validate all targets, current permissions, supported values, and expected versions together. Reject conflicting stale edits and require reinspection.
- Prepare required allocations, the Batch Reference identity, and restoration storage before mutation. Preparation failure leaves affected scene state unchanged and publishes no committed/restorable batch. For supported edits, preparation must leave a commit that cannot fail partway through.
- A registered scene exposing edit or resynchronize capability must register the hook matching each exposed capability: a scene exposing edit needs a normal-synchronization hook, and a scene exposing resynchronize needs a recovery callback. Neither capability requires the other's hook. Activation rejects a configuration missing a required hook, before descriptor publication.
- Expose complete new state or unchanged old state, never intermediate edits. After the complete atomic edit/restore commit, record committed state and mark the scene synchronizing. At the safe execution point invoke the host's registered normal-synchronization hook once; that hook owns the ordinary downstream notification/update, not a second notification or edit replay. Wrapping existing setters in notification batching is not proof of atomicity.
- Require synchronous host acknowledgement before terminal edit/restore success: confirmation that downstream state for every registered view is ready to render the committed scene. That set is the scene's views registered when the hook is invoked. View registration and unregistration are host scene work serialized at safe points, so they cannot change the set while the hook runs. Registering a new view of a scene is only complete once the host confirms that view's downstream state matches the current scene; if the host cannot confirm it, registration fails, or the scene becomes `needs_sync` and its views are blocked until a successful Resynchronize. A view never becomes renderable on unconfirmed downstream state. No image rendering or GPU convergence wait is required. Failure, exception, or inability to confirm readiness leaves the scene committed, marks synchronization failed and returns applied_with_sync_failure. There is no terminal success-now/synchronize-later outcome in v1. While the hook runs, committed/synchronizing is progress, not terminal success; cancellation or disconnect cannot report an already-committed change as a non-commit, and safe completion rules still apply.
- Ordinary synchronization is part of authorized edit/restore and needs no separate resynchronize capability. Explicit recovery does. A later incremental edit/restore cannot silently clear an existing synchronization failure: explicit Resynchronize remains necessary to establish whole-scene coherence again. An ordinary update must not report synchronization-ready success while that prior failure remains uncleared. The normal hook still runs once after such a commit; even when it confirms readiness, the edit/restore returns applied_with_sync_failure and the scene stays failed until a successful Resynchronize.
- Post-commit synchronization failure reports **edits applied with synchronization failure**, not rejection or rollback. The edit retains its Batch Reference and conditional restoration subject to normal conflicts/retention. Mark the affected registered scene not ready: every registered view of that scene is blocked, even if an individual renderer/index remains healthy. Other scenes remain usable unless the host identifies their downstream state as affected too. This conservative scene-wide scope is deliberate; v1 has no per-index dependency graph or partial-view recovery guarantee.
- Do not promise rollback of arbitrary external callback effects; callbacks must not observe intermediate batch edits, but their post-commit failure does not undo scene commit.
- Expose scene synchronization states `ready`, `needs_sync`, `synchronizing`, and `failed` (the frozen names; prose "synchronization required" means `needs_sync`). An explicit Resynchronize operation/viewer action targets the registered scene, requires that scene's read and resynchronize permissions under the caller's authority, and invokes a host recovery callback at a safe point. Rebuild downstream rendering state from the current scene; report ready only after the host confirms that state for all its registered views matches the current scene. Report transitions and success/failure; never replay the edit or change its committed outcome. No automatic retry loop.
- A non-ready synchronization state blocks new valid render outcomes, not inspection of the committed VSR scene, permitted history/status access, or otherwise-authorized edits/restorations. Those operations retain their existing permission, revision and conflict checks. A render refused for this condition reports sync_required, not the mutation-only applied_with_sync_failure code.
- Existing RenderIndex rebuild entry points require recovery validation. This is in-memory behavior, not process-crash recovery.

### 11. One-way Batch Restoration

**Batch Restoration** returns an eligible batch's parameters to recorded prior values without rewinding unrelated state. It is not another restorable Agent Edit Batch and creates no redo journal.

- Offer an authorized external operation and local Restore action. Both explicitly select the original batch using `target_batch_ref`, the complete launch-qualified Batch Reference, never an implicit most-recent batch or storage position. An external restoration has its own current `operation_ref`, distinct from that target and the original edit's provenance.
- Local recovery uses host-local correlation and authority, not an external ID/session/lease or competing controller, and remains available after Pi disconnects or agent edits are disabled. A newly attached authorized external session may also select a retained batch from an earlier session without its old secret or a prior inspection operation. Require current session proof, current read/edit permissions, valid targets and the journal's post-commit-version/eligibility checks at execution; no fresh-observation proof or old observation token is an input to restoration. The target reference alone grants no authority.
- Use the same preparation, scene-commit, synchronization, and conflict rules, with bounded temporary preparation memory rather than recursive redo storage. Preparation/conflict failure changes neither values, versions, nor original eligibility.
- Compare each affected object's current parameter version with its recorded post-commit version, plus identity/required references. Any subsequent parameter change on that object conflicts, including another parameter or change-back. Missing targets/incompatible references also reject unchanged. Other-object changes alone do not conflict.
- Restore only batch parameters, completely or not at all. Never force overwrite, partially restore, or apply a whole-object/whole-scene rewind.
- At commit, advance versions normally and consume original eligibility, even if synchronization subsequently fails. Report applied-with-synchronization-failure where appropriate. Restoring a newer batch cannot revive an older record.
- The same retained restore Operation Reference replays its outcome; changing target_batch_ref changes the canonical request and is not an identical retry. A different request against a known consumed Batch Reference reports already_restored. Unknown, expired, or wrong-launch Batch References report outcome_unavailable: never select another record, claim it never existed, or recreate eligibility.
- Commit releases the original restorable-batch position; release its payload when safe and retain only bounded history/results. Preserve active-work reservations and the existing visible-eviction policy. Distinguish restored, expired, and conflicting reasons while metadata remains retained.

### 12. Revision-pinned rendering

- The request names a registered view and desired scene/view revision tokens from inspection or completed edits. Both must match at safe-point execution; otherwise return superseded without rendering whichever state is now current.
- V1 render requests have no per-request width/height override. Use the registered view's current dimensions, which are covered by its view-revision token. Width/height must be positive integers within the configured integration limit, initially 1 through 1024 each. Invalid or oversized dimensions reject before backend rendering; do not silently clamp, downsample or resize the application's view. A successful PNG has exactly those validated dimensions. A resize changes the view revision and an old requested token returns superseded. A host may expose a separate bounded capture view, or the operator may resize an oversized native viewport; the API does not automatically adapt it.
- Matching tokens are necessary but not sufficient: the view's registered scene must also be synchronization-ready before backend rendering starts and before committing/publishing a successful render outcome. When revisions still match but the scene is not ready, return sync_required with no image. Do not wait implicitly for recovery, trigger resynchronization, retry automatically, or return a PNG merely labeled invalid. Safe-point refusal after admission consumes the admitted ID under the normal identity rules.
- Relevant changes during rendering prevent success. Successful results carry the exact matching tokens and satisfy the synchronization guard. Existing cancellation/deadline terminal rules still apply; no late synchronization or backend completion can revive a failed/canceled/timed-out request. Keep unsafe backend resources/slots until safe release even if a synchronization guard terminates the logical request. No historical rendering snapshots are retained; reinspection is required when requested state is gone. Another light may invalidate an image without invalidating an edit to an unrelated material.
- Retained completed images remain historical results with their original provenance under current read permission. Lookup/duplicate replay is not a new render and does not attest current scene readiness; a later synchronization failure does not rewrite an already-completed outcome.
- The logical deadline is 30 seconds from admission, including queue wait, safe-point wait, and rendering. Expired queued work never starts rendering; busy rejection is not admission. Do not promise portable convergence.
- Timeout/cancellation is terminal. Attempt backend cancellation where supported, discard late images as results of that request, and retain resources/scene slot until safe release. Report busy when necessary; never destroy live buffers to satisfy a logical deadline.
- Normalize results to PNG, 8-bit RGBA, sRGB RGB channels, straight alpha, top-left origin, x rightward and y downward. Normalize source buffers as needed and validate backend color/alpha handling.
- Color mapping: the registered view's Image Pipeline owns exposure and tone mapping and must produce display-referred linear color; the integration adds no tone mapping in v1. For linear color channels, clamp each to [0,1] (NaN maps to 0), apply the standard sRGB transfer function, then round to the nearest 8-bit value (encoded value × 255, exact halves round up). Pipelines deliver either float linear channels or 8-bit sRGB-encoded channels. Only an 8-bit sRGB-encoded, straight-alpha source passes through unchanged (its 8-bit alpha included). Every other source, including any float alpha, follows the clamp/quantize rules below. Clamp alpha to [0,1] (NaN alpha maps to 0), then quantize it to 8 bits by the same round-to-nearest rule as RGB (value × 255, exact halves round up); convert premultiplied sources to straight alpha, with RGB 0 where alpha is 0. Unpremultiply in linear space: a premultiplied 8-bit sRGB-encoded source is first decoded to linear, then unpremultiplied, then re-encoded by the rules above. This export rule does not change imported textures or sampler coordinates.
- Returned image ownership must survive live-buffer reuse. Arbitrary file export is not required: the client receives an image result, not an output-path capability.

These gates establish feasibility/interoperability; they do not replace acceptance testing of the complete contract:

## Testing Decisions

### Confirmed primary seam

The user already confirmed **one primary behavioral seam: the public headless integration API**, driven with real VSR Scenes and an application-owned execution loop. Test business behavior there rather than introduce testing interfaces throughout Scene/Object/rendering or duplicate it through ImGui.

Good tests assert responses, final scene state, authority, activity, resource bounds, restoration, and image provenance. Avoid private queue-layout/method-order assertions and aesthetic model judgments. Use deterministic clients, controlled monotonic time, and narrowly scoped host-boundary fault injection. Actual Pi interoperability is a separate acceptance check.

### Existing infrastructure and prior art

- Use the repository's Catch2 scenarios and CTest conventions. Scene, Object, and Parameter suites provide real-scene and delegate examples.
- Object Archive/component-serialization suites provide state-inspection/round-trip precedent, not proof of transactional restoration.
- RenderIndex tests use a small scene and CPU-capable helide without display/GPU requirements; reuse that approach for real rendering checks.

9. **Bounded paging:** test omitted/default and requested page_size values, invalid-value rejection without clamping, and valid size changes on continuation without cursor invalidation. Every continuation page uses a new Operation Reference/admission slot; intra-page safe-point slices retain that page's ID/slot. Identical-ID retries replay the retained page rather than fetching the next one, and cursors alone hold no slot across round trips. Use new request IDs for changed arguments. Enumerate large registries/scenes without full materialization, enforcing independent item/byte/field/work/scratch caps and explicit truncation/oversize/continuation/completion. Metadata/returned-value/membership/order/registration/handle changes invalidate cursors between and during pages; changing page size alone does not. Check tamper/session/query rejection, fairness, deadlines and unsupported providers. Discovery items carry current effective capabilities; a capability change on a listed target between pages returns cursor_stale.
10. **Images and render lifecycle:** use real headless rendering and an asymmetric oracle for orientation, channel order, sRGB, straight alpha, dimensions, and buffer lifetime. Assert view-owned dimensions with no request override and exact output size; accept positive integer sizes through the configured maximum, initially 1024 per axis. Reject invalid/oversized view dimensions before backend work without clamping/downsampling/view resizing. A resize invalidates the old view token; a separately registered bounded view supports capture when the native viewport is too large. Mismatched input revisions and relevant mid-render changes supersede; success identifies matching state and requires scene synchronization readiness at start and completion. Non-ready scenes return sync_required without image output, but already-completed historical results replay with their original provenance under read permission. Queue wait consumes the deadline; expired queued work never starts. Completed-before-cancel stays completed, canceled/timed-out late images never succeed, and non-interruptible resources remain safe. Test the color mapping with controlled pipeline outputs: out-of-range and NaN linear values and NaN alpha map as specified, fractional alpha (including a quantization midpoint) rounds to nearest, premultiplied 8-bit sRGB unpremultiplies in linear space, linear mid-gray encodes through the sRGB transfer function, 8-bit sRGB input passes through, and premultiplied input becomes straight alpha. Prefer robust tolerances to cross-device bit-exact pixels.
11. **Scene/control saturation and stalled cleanup:** mix external callers and multiple local windows/in-process callers in the single 32-slot integration pool; queued/running/yielded requests and retained backend work all count. At full capacity, both external work and local Restore/Resynchronize reject busy without admission, scene mutation, or an extra local queue. Local callers need no external session but gain no extra slots. Ordinary application work outside this API is not charged to the pool, while safe-access coordination remains required. Test an indefinitely non-releasing fake backend: retain its slot/resources, expose cleanup age/capacity, never infer a fault merely from elapsed time or force release, and keep bounded control/local Disconnect/revocation serviceable without a scene slot. Revocation must not reclaim unsafe resources to admit local recovery. An actual reported backend fault is shown distinctly. Verify busy rejection, 8-request external control bounds, priority/coalescing, metadata-only access, and no unbounded cleanup pool or automatic restart.
12. **Retention and feedback:** test defaults and smaller configured limits, payload-byte accounting, oldest-safe eviction and visible expiry, active reservations, request/status versus pre-commit restoration allocation failures, and disconnect survival without restart persistence. Distinguish VSR activity from client descriptions and logical outcomes from physical backend state. A new session with current proof/read authority may retrieve retained old-session results by complete Operation Reference, with original operation kind/provenance and no old secret. Deny foreign-session records without read permission for every covered target, including partial multi-target grants and callers entitled only to their own minimal receipts. Missing/evicted records report outcome_unavailable; lookup grants no cancel/replay/execution authority. Both edit and restoration conflicts identify operation kind and no commit, without requiring English parsing or mandatory finer subcodes.
13. **Descriptor and wire safety:** reject unsafe parents, symlinks, non-regular/pre-existing destinations without modification; a pre-existing `vsr-mcp-<launch_id>.json` fails activation closed without publishing under another name; check private access from creation and opened-file validation. Exercise directory selection through OS-runtime and explicit host configuration, wrong directory owner, insufficient owner access, group/other or ACL access, and an ancestry another account can replace/redirect. Environment/path labels never substitute for opened-directory validation. Invalid pre-existing locations fail without chmod/repair or unchecked fallback; new private directories are restrictive from creation. Validate equivalent platform account/ACL rules or report unsupported. Readers see absence or complete publication only after readiness. Exercise every schema/encoding/version/authority rule, no redirects/proxies/secret forwarding, concurrent launches, mismatch-safe cleanup, stale credentials, and unsupported platforms. Verify IPv4-only 127.0.0.1 and IPv6-only ::1 listeners, IPv6-only behavior established before binding, no wildcard/second-family listener, and mapped-address rejection in descriptor/Host. Inability to enforce these guarantees fails activation before publication. Verify the private descriptor retains its required launch credential but no session fields/secret, public session IDs are not secrets, and neither secret leaks through URLs/model output/activity/logs.

### Thin adapter checks and end-to-end acceptance

- **MCP:** real authenticated loopback requests validate parsing, security, lifecycle, qualified Operation References, launch-qualified Batch References and distinct restoration selectors, initial/current capability policy and cross-session payload gates, view-owned dimensions without request overrides, and machine-readable outcome mapping (including sync_required and operation-kind-qualified conflict) against the public API without duplicating its full suite. Required codes and commit/no-commit meaning survive the chosen carrier; no client test depends on parsing an English error message.
- **Pi:** first prove hidden bootstrap/proofs, reconnect and renewal with the actual gateway/adapter. On a new attachment, verify supported client workflows invalidate cached observations as current and inspect live targets before forming new version-pinned edits/renders; cached historical lookup is not a refresh. Verify this client behavior without adding a server-side observation-proof mechanism. Then start the app before Pi and complete inspect/image/edit/fresh-render/restore/detach on the procedural fixture. Include second-client denial and abandonment. Record model/image prerequisites and whether an adapter was actually necessary.
- **Viewer:** smoke-test connection information, truthful activity/results, edit-disable versus disconnect, restoration after Pi exits, and synchronization recovery. Keep business-rule tests at the headless seam.
- **Build configurations:** cover server disabled/enabled, headless hosting, and viewer integration. Pi, Lua, and UI must not become mandatory for unrelated consumers.

Required rendering acceptance must provision a working helide device and actually render; a missing device makes that acceptance attempt unsuccessful. General developer suites may report explicit environment skips, but those are not feature evidence. In this workspace, install freshly built libraries before testing because the generated environment's installed-library search path can outrank test-binary build-tree lookup. Verify the tests exercise current libraries, not stale installed copies.

## Out of Scope

- Remote or browser-origin access, automatic application scanning, silent attachment/takeover, multiple external sessions, or per-scene controller partitioning.
- Embedding Pi in VSR, making it a runtime framework dependency, or requiring a companion MCP process.
- Viewer chat input, full conversation mirroring, exposed agent reasoning, or advanced image-comparison UI.
- Agent-side object creation/deletion, material-subtype replacement, reference/array edits, unlisted built-in parameter edits, dataset import, application-source modification, renderer-internals diagnosis, arbitrary commands, or file operations. Lua remains a possible later separately authorized capability.
- Whole-task transactions, application-wide undo/redo, restore-of-restore, forced/partial restoration, durable audit/session state, cross-restart undo, or crash-consistent scene transactions.
- Rollback of arbitrary post-commit callback effects, guaranteed immediate backend interruption or eventual cleanup, forced/automatic recovery of unreleasable backend work, crash-descriptor cleanup daemons, or same-account malicious-process isolation.
- Guaranteed convergence, historical rendering snapshots, automatic resynchronization loops, per-index synchronization dependency graphs/partial-view recovery, multi-scene registered views, bulk array/oversized-field export, full-scene inspection snapshots/lists, or filesystem browsing.
- Weaker ownership via TCP/launch credential alone, replacement of another launch's descriptor, redirects/proxies for control connections, or unvalidated platform security claims.
- Exact-decimal lexical validation or equivalence between two-stage and direct decimal-to-binary32 conversion.
- Native archive-schema or imported-image orientation changes merely to support integration, or aesthetic improvement as an automated correctness criterion.
- Publishing these local working artifacts to GitHub without explicit authorization.
